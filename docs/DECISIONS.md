# Решения SCM (ADR)

## D-001. SCM = Scientific Content Machine

**Решение:** проект развивается как детерминированная машина научного
контента, а не как «ещё один генератор текста LLM».

**Причина:** нужен проверяемый источник, повторяемость и коммерческая ветка
без подмены истины.

## D-002. Контент без LLM

**Решение:** текст берётся из источников; LLM не является источником факта.
Модель допустима как черновик/перевод, но результат проходит quality gate.

## D-003. Оракул ставит `PROVEN`

**Решение:** `PROVEN` ставит RII/KERN/Z3/Lean/PTE или владелец. Агент оставляет
`UNPROVEN`.

## D-004. Отдельная Knowledge Base SCM

**Решение:** `data/knowledge.db` хранит документы SCM, утверждения, заметки,
решения и метрики. Корпус NYUUI не дублируется.

## D-005. Book-фильм отдельным модулем

**Решение:** `book_film.py` — светлый книжный видео-движок; `moku_film.py` —
тёмный 3D. Оба доступны в `/ab`.

## D-006. Эталон голоса — Светлана

**Решение:** `ru-RU-SvetlanaNeural` — основной голос. При лимите/сбое edge
включается адаптивная цепочка `piper → google_tts → espeak → сонификация`;
Google TTS используется только как резерв, а не как подмена по умолчанию.
Состояние лимитов хранится в `data/audio/voice_health.json`.

## D-007. Пост ≠ радио

**Решение:** пост завершается «Разбор завершён», радио — «Эфир продолжается».
Это разные регистры.

## D-008. Документация тем же коммитом

**Решение:** изменение поведения без обновления docs не принимается.

## D-009. Только SCM

**Решение:** агент не меняет RII/KERN/NYUUI/АССИСТЕНТ и другие проекты без
отдельного задания. Внешние системы — оракулы и источники, не части репозитория.

## D-010. D1-Primary и один writer

**Решение:** Cloudflare D1 — источник истины для CI-записи. Локальный
`data/science.db` — кэш и не коммитится в `main`. Мутации защищены lease-lock
в D1/KV; второй раннер уходит в `deferred`, а не публикует параллельно.
Git-зеркала и статические хостинги — только read-only. Снимок состояния
хранится в GitHub Release `state-backup`; R2-бэкап — опционально.

## D-011. Online-пост обязан нести проверяемую математику

**Решение:** пост тира `online`/`curriculum` публикуется, только если у него
есть формула или код. Иначе он не попадает в очередь (`Post.validate`) и
уходит в карантин на публикации (рубеж `content`).

**Причина:** «сырые» источники (Wikipedia, arXiv, рекурсивный обход категорий)
отдают энциклопедический текст без формулы. В ленте такой пост выглядит
кривым: в подписи нет `Инвариант:`, остаётся generic-шаблон и
`Первоисточник: Wikipedia (ru)`. Канон, фундамент, офлайн-бункер, история и
ручные посты правилом не затрагиваются — у них формула есть всегда либо
добавляется осознанно.

## D-012. Тесты герметичны к `.env`

**Решение:** `tests/__init__.py` отключает автозагрузку проектного `.env`
(`_load_dotenv`) и снимает креды площадок из окружения.

**Причина:** `load_config()` подгружал `.env` в общий `os.environ`, из-за чего
на машине оператора падали `test_metrics` ×3 и
`test_recovery.test_requires_username` — реальные токены меняли проверяемое
поведение. Тесты обязаны опираться только на явно переданные значения.

## D-013. Карантин (`rejected`) не реплицируется как «слабый» статус

**Решение:** в CRDT-ранге статусов `rejected` стоит **выше** `ready`
(`ready < publishing < failed < rejected < published`) — в `storage.py`, в
`cloudflare/worker.js` и в Lean-модели (`formal/Invariants.lean`).

**Причина:** ранга не было, поэтому `rejected` имел неявный вес 0 и любой
`pull` из D1 (где ещё лежал `ready`) откатывал карантин обратно в очередь —
и `standards`/`canon_gate` теряли отбракованные посты. Ручной `--force`/`/force`
дополнительно обязан обходить гейт зрелости (как и паузу, интервал и Hawkes):
иначе локально (без `GITHUB_TOKEN`) канон нельзя опубликовать вручную.

## D-014. Пауза (`paused`) реплицируется из D1

**Решение:** `paused` убран из `KV_LOCAL_ONLY` и добавлен в `KV_REMOTE_WINS`;
пульт (`/pause`, `/resume`) сразу пишет паузу в D1 (`push_state`).

**Причина:** Worker/webhook ставит `paused=1` в D1, но Python-конвейер его не
видел (ключ не реплицировался) — `/pause` не останавливал публикации.
CI эфемерен, поэтому локальная пауза без push исчезала к следующему прогону.

## D-015. Осиротевшие публикации/метрики не роняют слияние; `INV-3` держится флагом

**Решение** (все шесть частей вместе):
1. `merge_snapshot` пропускает `publications`/`metrics`, для которых нет своего поста
   (иначе `FOREIGN KEY` откатывал **всю** транзакцию слияния).
2. Устаревший `card_file_id` снимается `invariants --repair`, ставя флаг
   `meta.card_file_id_cleared`, который `_join_post` уважает — в том числе при импорте
   в **пустую** БД (так делает CI).
3. `state_export.push` **прерывается** на первом непринятом батче (`aborted`): иначе
   пост мог не дойти до D1, а его публикация — дойти (первопричина «сирот»).
4. Worker `/api/state` **не принимает** `publications`/`metrics` без своего поста
   (D1 не умеет `FOREIGN KEY`) — отдаёт `skipped` в ответе.
5. `harvest` уважает сбой `pull` (симметрично `publish_next`): при недоступном D1
   он не «переживает» сбой добычей. Раньше добыча шла на пустой БД, заново
   собирала канон и **пушила** его в D1 — остаточный канал того же перевыпуска.
6. `invariants --repair` восстанавливает **потерянные** строки публикаций (INV-2) из
   фактов о вышедшем посте: `card_file_id` → telegram, `meta.threads_video_id` → threads,
   иначе manual. «published без публикации» — это не «не публиковался», а потеря строки;
   восстановление закрывает INV-2 и **не даёт перевыпустить** пост.

**Причина:** в D1 жили 2 публикации без поста (`c5a6404d`). Падал `state --pull`;
откат терял состояние D1 целиком → CI заново харвестил канон и **перевыпускал уже
вышедшие посты** (Архимед §1.3 — всплыл на сайте; Пифагор §1.1 — ушёл в Telegram/Threads).
Устаревший `card_file_id` (след тех же откатов) стереть не удавалось: слияние «непустое
побеждает» — и INV-3 падал на каждом прогоне.

## D-016. Репликация в D1 атомарна; дрейф состояния лечится в CI

**Решение:**
1. `state_export.push` шлёт **самосогласованные пакеты**: пост уходит в одном запросе
   со своими `publications`/`metrics` (нарезка по постам). Зависимые строки без поста —
   отдельным пакетом (Worker их отклонит), независимые таблицы — отдельно.
2. Worker `/api/state` применяет каждый запрос **одной транзакцией** (`env.DB.batch`):
   при сбое откатывается весь набор — частичной реплики не остаётся.
3. В CI перед `invariants` стоит шаг автолечения: `invariants --repair` + `state --push`
   (best-effort) — остаточный дрейф лечится на каждом прогоне.

**Причина:** с `push-abort` репликация всё равно шла по таблицам отдельными запросами,
поэтому сбой ровно между батчами `posts` и `publications` мог оставить в D1 «published
без публикации» — обратную сторону «сироты» (INV-2). Атомарный пакет «пост + его строки»
делает рассогласование недостижимым, а CI-шаг лечит наследие прошлых сбоев.
